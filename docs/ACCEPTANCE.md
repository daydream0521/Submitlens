# SubmitLens — 两个真实案例与验收记录

## 案例 A：传智杯 AI 创新应用挑战赛

**输入来源**：用户提供的《赛道介绍.md》。下列是供 AI 提取核对的**人工预期清单**，不表示产品已经通过测试。

| 交付单元 | 必交 | 原文依据 | 明确约束 | 首版检验 |
|---|---|---|---|---|
| 代码仓库与提交历史 | 是 | `2.1 代码仓库与演进记录` | GitHub/Gitee；须可供评审访问；细粒度 Git 提交 | 链接/材料存在可记；访问与历史质量人工复核 |
| AI 对话与 Prompt 记录 | 是 | `2.1 代码仓库与演进记录` | 至少 3 个核心功能的完整迭代 Prompt 链 | 记录材料存在；链条数量/完整性人工复核 |
| README 复现说明 | 是 | `2.2 复现性声明与重现指南` | 环境配置、依赖、环境变量模板；10 分钟复现指南 | README 文件存在；实际复现人工复核 |
| 演示视频 | 是 | `2.3 演示视频与技术文档` | MP4、5–8 分钟、1080p；至少 2 分钟 AI 协同开发过程 | MP4 与时长自动；分辨率及内容人工复核（V1 不检查分辨率） |
| 技术文档 | 是 | `2.3 演示视频与技术文档` | PDF，不超过 30 页；涵盖意图控制、架构与可复现性 | PDF 格式/页数自动；内容人工复核 |

**不能误提成必交成果**：推荐选题表中的 10 个方向、时代背景文字、评分维度和奖项比例。报名资料与参赛组别信息属于参赛办理事项，不能作为交付包中必须存在的成果文件自动检查。

**关注原文表述**：材料中的 `MP41080p` 是紧连书写；交付清单应表达为 MP4、1080p，避免模型遗漏分辨率约束。开发 MVP 暂不增加分辨率自动检测。

### 验收操作

1. 新建「竞赛」项目；上传实际《赛道介绍.md》。
2. 提取并确认上述核心条目。重点观察 5–8 分钟、≤30 页和 ≥2 分钟内容要求是否正确、是否可追溯到段落。
3. 上传实际 README、PDF、MP4、Prompt 记录和代码资料或仓库链接。
4. 检查 PDF 页数及 MP4 时长；为视频内容、Git 历史等标注人工状态。
5. 上传不同内容的新视频替换旧文件，确认时长重新计算、人工复核恢复待复核。
6. 导出 ZIP，检查压缩包实际文件及 Markdown 报告与当前状态一致。

## 案例 B：Ubuntu 课程实验

**输入来源**：用户此前课程实验的真实任务文档（当前启动包未包含该文件）。不预设截图张数、具体任务数量或报告格式，避免制造虚假金标准。

获得原始要求文件后，按以下结构人工整理，不创建新的评测系统：

| 原文位置 | 实际要求 | 必交/建议 | 对应成果 | 自动可验条件 | 人工复核内容 |
|---|---|---|---|---|---|
| 待填真实位置 | 待填 | 待填 | 报告/代码/截图等 | 文件存在、格式、数量等文中明确条件 | 实验结果与运行正确性 |

操作流程必须与竞赛一致：导入→提取→确认→上传→关联→检查→替换→导出。

## 已知关键行为的最少检查

| 操作 | 预期结果 | 保护的失败场景 |
|---|---|---|
| 保存项目后刷新页面 | 项目名、类型和原始任务说明仍然存在 | 项目仅存在内存中、刷新丢失 |
| 在要求内上传文件 | 自动关联到当前要求 | 文件进入公共库但用户找不到对应要求 |
| 同一文件关联两个要求 | 两条要求均可引用，不重复存储 | 多对多关联被错误限制 |
| 上传 09:21 视频，要求 05:00–08:00 | 显示实际时长、上限及不通过 | 只根据扩展名就判定通过 |
| 旧视频失败，新视频 07:12 设为提交文件 | 新视频时长通过，旧失败不影响最终判断 | “任一候选失败则失败”的聚合错误 |
| 已人工确认的视频被替换 | 复核重新变为待复核 | 旧证据的人工结论错误沿用 |
| PDF 31 页，限 30 页 | 不通过，显示 31 / 30 | 页数门限未实际执行 |
| PDF 损坏无法读取 | 显示检查异常，不声称自动通过 | 读取错误被吞掉 |
| 导出后更新材料 | 界面提示需要重新导出 | 使用旧 ZIP 误当新成果 |
| 禁用 AI API、手动录入要求 | 仍可验收、导出 | 核心业务被 LLM 服务中断拖垮 |

阶段 1 只验收「创建项目→粘贴并保存任务说明→刷新/重启后仍可读取」；其余检查待对应模块开发时执行。不要为了这些清单在项目开始时一次性搭建复杂测试框架。
