# SubmitLens — 产品需求文档（PRD V1.0）

**交付目标**：2026-11-18 前完成可复现、可演示的个人赛 MVP。

## 1. 产品定义

SubmitLens 是面向大学生**竞赛和课程作业交付**的验收工作台。用户输入任务说明、上传已有成果，系统建立要求与文件的关联，执行可核对的检查，输出问题清单及交付材料包。

**核心任务**：确认“要交什么、已有材料对应什么、哪里不符合、最终导出什么”。

**区别于通用 LLM/Agent**：要求和文件关联持久保存；检查依据与结果可追溯；文件变动后相关结果更新；可以导出真实文件。LLM 只参与自然语言要求提取和文件关联推荐，不直接宣布验收通过。

**首版边界**：单用户、本地优先、桌面 Web；课程与竞赛共用流程，不做两个产品。

## 2. 目标用户与真实场景

- **竞赛交付**：用户上传《赛道介绍.md》，识别代码仓库、Prompt 记录、README、视频及 PDF 技术文档要求；上传成果后检查文件格式、页数、时长等条件，整理提交包。
- **课程交付**：用户粘贴教师任务说明或上传课程文档，将实验报告、脚本、截图等对应到要求；检查明确的文件条件，实验是否正确由用户复核。

两个案例仅用于证明同一流程适用于两种来源；不另设「竞赛引擎」「课程引擎」。

## 3. 用户操作流程

1. **项目**：新建项目，填写名称、选择「竞赛 / 课程」。首页能再次打开已有项目。
2. **任务说明**：选择「粘贴文本」或「上传文件」（PDF/DOCX/MD/TXT）；可跳过 AI，手动新建要求。
3. **要求清单**：AI 提取交付物、必交/建议、格式/数量/时间限制和原文位置，按交付物分组。用户可快速确认整份清单，也可查看出处、编辑、删除、添加、拆分/合并。未确认的 AI 草稿不参与验收。
4. **成果**：支持项目文件库**批量上传**，也支持点击具体要求**定向上传**；可从已上传文件选择，避免重复存储。AI 可以建议关联，用户决定实际用于交付的文件。
5. **预检**：运行客观检查，展示实际值、要求值、原文出处、检查时间和具体问题。无法自动判断的内容进入人工复核。
6. **修复**：替换、移除、重新关联或更改已确认要求后，仅相关检查结果更新；旧文件的人工复核不得自动沿用到新文件。
7. **导出**：选择最终文件，查看目录，导出带真实材料的 ZIP + `submission_report.md`。未完成项目也可导出，报告如实列出未解决项。

**主要界面**：①项目与要求；②成果验收；③交付中心。项目列表为①的入口。

## 4. 功能范围与验收条件

### P0. 项目与任务说明

- [ ] 创建、打开、重命名、删除本地项目；刷新页面不丢数据。
- [ ] 输入任务纯文本（包括粘贴的多段文本）；原文持久保存，保留换行与段落。
- [ ] 上传 PDF/DOCX/MD/TXT 作为任务说明；可查看解析后的文本及出处。
- [ ] 允许仅靠手动录入要求完成后续全部流程，不依赖 API Key。

### P0. 要求提取与确认

- [ ] LLM 从任务文本中提取明确的交付要求，并按交付物组合格式、数量、内容限制。
- [ ] 每条保留原文依据：粘贴文本按段落；MD 按标题/行；PDF 按页；DOCX 按段落。
- [ ] 区分**必交 / 建议**；不把选题参考或背景描述变成硬性验收项。
- [ ] AI 草稿允许整体确认、逐项修改、删除、拆分/合并、手动新增；用户确认后才进入正式验收。
- [ ] AI 失败、不可用或结果为空时，原始任务说明不丢失，能人工录入要求。

### P0. 成果文件与关联

- [ ] 上传并管理 PDF、文档、图片、MP4、代码文件与 ZIP 等一般成果。
- [ ] 支持**项目级批量上传**、**要求内定向上传**、**选择已上传文件**三种入口。
- [ ] 要求与文件是多对多关系，保存后刷新仍在。
- [ ] 单文件交付要求可以从候选文件中**指定一份实际提交文件**；数量要求使用用户选定的互不重复文件集合。不能因旧版本失败影响新版本。
- [ ] 删除文件或解除关联后，检查状态及时更新；替换文件视为新上传版本，旧文件人工复核失效。

### P0. 验收

- [ ] **自动检查仅限**：文件存在、格式、PDF 页数、MP4 视频时长、选定文件数量。
- [ ] 检查条件来自用户**确认后的要求**，不能根据文件名或模型建议自行补造阈值。
- [ ] 每项客观检查显示「实际值 / 要求值 / 依据 / 检查时间 / 结果」。
- [ ] 内容真实性、代码正确性、README 可复现性、视频语义等标为人工复核，提供人工「符合 / 不符合 / 未复核」及可选备注。
- [ ] 用户人工确认与系统自动检查分别标识，不能将自评称为“系统验证”。
- [ ] 明确失败 ⇒ 不通过；无明确失败但存在未复核或检查异常 ⇒ 待复核；适用检查全部通过、需复核项都已确认 ⇒ 通过。人工确认不能覆盖客观失败。
- [ ] 建议项未提交时不计入必交项目的失败数；异常读取要显示异常原因。

### P0. 导出

- [ ] 用户勾选实际要交付的文件，预览文件目录。
- [ ] ZIP 实际包含选定文件与 `submission_report.md`；同名文件通过目录区分，不覆盖。
- [ ] 报告包含：必交/建议、各项状态、要求来源、对应文件、客观检查数据、人工确认与未解决问题。
- [ ] 不阻止未完成项目导出；文件或要求再次改变时，提示当前导出包可能过期，需重新导出。

### P1. 完成 P0 后的界面精修

- 以卡片、状态色、进度分布和文件类型标识展示检查清单；状态可以筛选和展开详情。
- 优化批量上传进度、空状态、文件替换反馈、响应式排版与动画节制。
- 可视化展示以**帮助定位不通过项**为目标，不开发关系网络动画或大屏装饰。

### 明确排除

多 Agent、RAG/向量数据库、聊天入口、自动编写作业、代码自动执行、OCR、视频语义识别、GitHub 授权同步、多账号协作、教务平台对接、在线提交和复杂历史版本管理。

## 5. 用户可见状态

| 类型 | 标签 | 适用情况 |
|---|---|---|
| 综合验收 | 通过 | 自动检查合格、所需人工复核已完成 |
| 综合验收 | 不通过 | 缺少必交证据、客观条件失败或人工判定不符合 |
| 综合验收 | 待复核 | 尚有需要人工确认的条件，或读取异常待处理 |
| 结果依据 | 自动通过/自动不通过 | 有程序检查与客观数据 |
| 结果依据 | 人工确认/人工判定不符合 | 用户主动复核 |
| 结果依据 | 检查异常 | 文件损坏、无法读取元数据等，展示原因 |

可选/建议要求默认不影响必交验收聚合。综合状态不是简单以所有关联文件中“任一失败”判断：单个交付物以用户**选定文件**检查，多文件数量要求以**选定集合**检查。

## 6. 上传规格与约束（产品初始值，不是赛事要求）

| 类型 | 单文件上限 | 首版处理 |
|---|---:|---|
| 任务说明 PDF/DOCX/MD/TXT | 50 MB | 提取文字与来源位置 |
| 图片 | 20 MB | 关联、基本预览和文件计数；不 OCR |
| MP4 视频 | 1 GB | 读取元数据与时长，不发送至 LLM |
| ZIP/普通成果 | 1 GB | 保存、关联、导出；不自动解压执行 |

上传显示文件名称、大小、进度与失败原因。超过限制要明确告知具体上限。任务文档上传成功不代表文本解析完整；提取失败可以改为粘贴文本。开发部署按本地单用户处理，不增加云存储。

## 7. 首版体验要求

- 入口首选「粘贴文本」「上传文件」，无需教学式长篇介绍。
- AI 提取完直接展示可扫读的分组清单，突出数字和格式限制。用户可整单确认，不强迫阅读整份原文；任何一项可点开原文定位。
- 成果页优先显示“不通过”“待复核”，其次是已通过；点击要求可直接上传、选择文件或查看证据。
- 每条问题都告诉用户**哪里不符合、具体数值和下一步操作**，不以泛泛的 AI 建议替代检查结果。
- 所有用户可见文字必须符合 `UI_COPY.md`；不以防御性说明填满界面。

## 8. 两个真实验收案例

**案例 A：传智杯（已有 `赛道介绍.md`）**

- 规则期待：代码仓库及 Git 演进记录、≥3 组完整 Prompt 开发链、README 复现指南、MP4 5–8 分钟且含 ≥2 分钟 AI 协同过程、技术文档 PDF ≤30 页。
- 自动可验：文件存在、MP4 格式/时长、PDF 格式/页数；Prompt 链是否完整、Git 历史质量、复现性和视频语义仍需人工复核。
- 路径：要求提取→人工确认→上传实际材料→检查→替换视频→复核状态失效→ZIP/报告导出。

**案例 B：Ubuntu 课程（需使用真实课程任务说明）**

- 从真实任务说明中人工整理期待清单；不得从想象中添加“必须有多少张截图”等条件。
- 路径与 A 完全相同，成果为报告/脚本/截图等，实验正确性由人工复核。

仅两份人工整理的预期清单作为提取对照；重点核对关键约束漏提、错提和误将建议当必交，不建设额外 Benchmark 平台。

## 9. 成功标准

1. 两种任务来源（粘贴文本、上传文档）均能形成可编辑要求清单。
2. 两个真实场景均通过同一套「导入→确认→关联→预检→导出」流程。
3. 用户可主动定向上传，文件替换、删除、取消关联不会留下虚假的通过状态。
4. 自动判断有可复核数据，人工判断有清晰来源；输出的是实际 ZIP 文件与 Markdown 报告。
5. 他人可凭 README 在本地完成核心流程；无 API Key 时可手动录入并运行验收。

## 10. 比赛交付约束（依据上传的《赛道介绍.md》）

- **省赛提交截止：2026-11-18**。
- Git 仓库细粒度提交，不得一次性提交全部功能；至少 3 个核心功能的真实 AI 协作 Prompt 链。
- README 含环境配置、依赖、环境变量模板，并支持 10 分钟复现说明。
- 演示视频 5–8 分钟（MP4，原要求同时注明 1080p），至少 2 分钟 AI 协同开发过程；PDF 技术文档不超过 30 页。
- 评审关注：过程可复现 25%，实际价值 25%，方法创新/意图控制 20%，工程 15%，体验 15%。

比赛要求是**参赛者的材料交付约束**，不要将其硬编码为 SubmitLens 所有项目的通用规则。
