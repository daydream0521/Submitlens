## 1. 第三阶段用户闭环

项目中已有确认后的要求清单。用户可以：

1. 在项目级文件库一次上传多份成果；文件列表显示原名、类型、大小及上传时间。
2. 打开具体交付要求，直接为该要求上传一个或多个文件，上传成功后自动建立关联。
3. 在要求内「从文件库选择」已有文件，无需二次上传；同一文件可以关联多条要求。
4. 一个要求可以关联多个候选文件；单件交付需求可以选定一份**最终提交文件**；数量要求可以选择多个文件集合。同一文件不重复计数。
5. 解除关联、删除文件、替换文件后，列表与关联状态即时正确更新；旧文件不能被误当成新文件。刷新浏览器、重启后端后依然保留所有项目文件和关联。
6. 查看紧凑的「要求—证据覆盖视图」：要求按「已有选定文件 / 尚未关联」分组，点击一条要求能看到关联的文件，点击文件能看到它对应的要求。此时是**证据覆盖**，不能宣称自动验收通过。

优先保证定向上传与文件关联顺畅，其次做项目级批量上传。可为候选文件提供基于文件名/类型的建议，但建议必须由用户确认；不要在本阶段引入多 Agent、向量库或大规模证据内容理解。

## 2. 文件限制与实现边界

- 任务文档上限仍为 50 MB，不改变阶段二规则。
- 成果上传初始限制：图片 20 MB；视频、ZIP、普通归档最大 1 GB；文档及一般文本成果尽量沿用 PRD 的类别限制。超限须显示准确提示。
- 视频 / ZIP 等大文件应**分块写入本地磁盘**，不能一次性读取整个文件进入内存。上传中显示基本进度或加载反馈，失败时应清理未完成文件。
- 上传文件用内部唯一 ID 对应实际存储路径；保留 `original_name` 用于展示与后续导出；同名文件不能相互覆盖。不要用用户传入的文件名直接拼接服务器路径。现阶段无须哈希或完整历史版本管理。
- 不解压执行陌生 ZIP，不运行用户上传代码，不做视频识别与 PDF 内容语义检查。
- 文件删除应同步删除它在当前项目的要求关联；替换文件应使用新 ID，新证据不继承旧证据的人工确认。后续阶段才实现实际预检和人工复核结果，因此本阶段不要假造“自动通过”的状态。

## 3. 数据与接口：沿用现有项目结构做最小扩展

- `artifacts`：id、project_id、原文件名、内部存储位置、类型/扩展名、大小、上传时间。
- `requirement_artifacts`：requirement_id、artifact_id、是否选为本要求实际交付证据；确保同一对关联不重复。

接口可按现有 FastAPI 路由习惯实现：上传成果、列出/获取文件、删除文件、绑定/解绑要求、选择/取消选择最终文件、查看双向关联。

不要单独开发通用事件总线、文件版本系统、抽象 Repository 层、复杂校验门禁或自动分类框架。
